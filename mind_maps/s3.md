S3 Objects Overview:
├── Key:
│   ├── Definition: The FULL path of the object
│   ├── Examples:
│   │   ├── s3://my-bucket/my_file.txt
│   │   └── s3://my-bucket/my_folder/another_folder/my_file.txt
│   ├── Composition:
│   │   ├── Prefix + Object Name
│   │   └── Example: s3://my-bucket/my_folder/another_folder/my_file.txt
│   └── No Directories Concept:
│       └── Keys are long names with slashes ("/") but no actual folders

├── Object Values:
│   ├── Content of the object body
│   ├── Max Object Size: 5TB (5000GB)
│   └── Special Rules:
│       └── If > 5GB, must use "multi-part upload"

├── Metadata:
│   ├── Definition: List of text key/value pairs
│   ├── Types:
│   │   ├── System Metadata
│   │   └── User Metadata

├── Tags:
│   ├── Definition: Unicode key/value pairs
│   ├── Max Number of Tags: Up to 10
│   ├── Purpose: Useful for security/lifecycle management

├── Versioning:
│   ├── Feature: Version ID is created if versioning is enabled



S3 Static Website Hosting:=
├── Feature: S3 can host static websites accessible on the Internet
├── Website URL:
│   ├── Format (varies by region):
│   │   ├── http://bucket-name.s3-website-aws-region.amazonaws.com
│   │   └── http://bucket-name.s3-website.aws-region.amazonaws.com
├── Common Error:
│   ├── Error: 403 Forbidden
│   └── Solution: Ensure the bucket policy allows public reads


Amazon S3 Versioning:
├── Feature: Allows versioning of files in S3
├── Bucket Level:
│   ├── Versioning is enabled at the bucket level
│   ├── Overwriting files (same key) will update the version (e.g., 1, 2, 3, …)
├── Best Practice:
│   ├── Protects against unintended deletions (versions allow restoration)
│   └── Enables easy rollback to previous versions
├── Notes:
│   ├── Files not versioned before enabling versioning will have version "null"
│   ├── Suspending versioning retains previous versions (does not delete them)



S3 Replication:
├── Requirements:
│   ├── Versioning must be enabled in both source and destination buckets
│   ├── Proper IAM permissions must be granted to S3
├── Types of Replication:
│   ├── Cross-Region Replication (CRR):
│   │   ├── Use cases: Compliance, lower latency access, replication across accounts
│   ├── Same-Region Replication (SRR):
│       ├── Use cases: Log aggregation, live replication between production and test accounts
├── Behavior:
│   ├── Copying is asynchronous
│   ├── Replication applies only to **new objects** after replication is enabled
│   └── Existing objects can be replicated using S3 Batch Replication:
│       ├── Replicates existing objects
│       └── Replicates objects that failed replication
├── DELETE Operations:
│   ├── Optional: Replicate delete markers from source to target
│   ├── **Deletions with a version ID are not replicated** (to avoid malicious deletes)
├── No Replication Chaining:
│   └── Objects created in one bucket are not replicated to a third bucket through intermediary replication (e.g., Bucket 1 → Bucket 2 → Bucket 3)


S3 Storage Classes Overview
├─ Storage Classes
│   ├─ Amazon S3 Standard - General Purpose
│   ├─ Amazon S3 Standard-Infrequent Access (IA)
│   ├─ Amazon S3 One Zone-Infrequent Access
│   ├─ Amazon S3 Glacier Instant Retrieval
│   ├─ Amazon S3 Glacier Flexible Retrieval
│   ├─ Amazon S3 Glacier Deep Archive
│   └─ Amazon S3 Intelligent-Tiering
│
├─ Class Transition
│   └─ Manual or automated with S3 Lifecycle configurations
│
├─ Durability
│   ├─ 99.99999999999% durability (11 9's) across multiple AZs
│   ├─ Loss rate: 1 in 10 million objects every 10,000 years
│   └─ Same durability for all classes
│
├─ Availability
│   ├─ Defined by storage class
│   ├─ S3 Standard example: 99.99% (53 min downtime/year)
│   └─ Varies with cost and use case
│
├─ S3 Standard - General Purpose
│   ├─ 99.99% Availability
│   ├─ Low latency, high throughput
│   ├─ Handles 2 concurrent facility failures
│   └─ Use Cases: Big Data, mobile, gaming, content distribution
│
├─ S3 Classes for Infrequent Access
│   ├─ Less frequently accessed, but rapid when needed
│   ├─ Cheaper than S3 Standard
│   ├─ Amazon S3 Standard-Infrequent Access
│   │   ├─ 99.9% Availability
│   │   └─ Use Cases: Backups, disaster recovery
│   └─ Amazon S3 One Zone-Infrequent Access
│       ├─ 99.5% Availability
│       ├─ Data stored in 1 AZ (failure results in data loss)
│       └─ Use Cases: Secondary backups, recreatable data
│
├─ S3 Glacier Classes (Archiving/Backup & Low Cost)
│   ├─ Pricing: Storage + Retrieval Costs
│   ├─ Amazon S3 Glacier Instant Retrieval
│   │   ├─ Millisecond retrieval
│   │   ├─ Minimum storage: 90 days
│   │   └─ Use Case: Access once per quarter
│   ├─ Amazon S3 Glacier Flexible Retrieval
│   │   ├─ Retrieval options:
│   │   │   ├─ Expedited: 1-5 mins
│   │   │   ├─ Standard: 3-5 hours
│   │   │   └─ Bulk: 5-12 hours
│   │   ├─ Minimum storage: 90 days
│   │   └─ Formerly: Amazon S3 Glacier
│   └─ Amazon S3 Glacier Deep Archive
│       ├─ Retrieval times:
│       │   ├─ Standard: 12 hours
│       │   └─ Bulk: 48 hours
│       └─ Minimum storage: 180 days
│
└─ S3 Intelligent-Tiering
├─ Small monthly monitoring fee
├─ Automatic object movement between tiers:
│   ├─ Frequent Access tier (default)
│   ├─ Infrequent Access tier (no access for 30 days)
│   ├─ Archive Instant Access tier (no access for 90 days)
│   ├─ Archive Access tier (customizable: 90+ days)
│   └─ Deep Archive Access tier (customizable: 180+ days)
└─ No retrieval charges



Object Encryption
├─ Overview
│   ├─ 4 Encryption Methods
│   │   ├─ Server-Side Encryption (SSE)
│   │   │   ├─ SSE-S3 (Amazon S3-Managed Keys)
│   │   │   ├─ SSE-KMS (AWS KMS Keys)
│   │   │   └─ SSE-C (Customer-Provided Keys)
│   │   └─ Client-Side Encryption
│   └─ Importance: Know which method is suitable for different scenarios (e.g., exams).
├─ Server-Side Encryption (SSE)
│   ├─ SSE-S3: Amazon S3-Managed Keys
│   │   ├─ Managed by AWS
│   │   ├─ AES-256 encryption
│   │   ├─ Header: `x-amz-server-side-encryption: "AES256"`
│   │   └─ Default for new buckets/objects
│   ├─ SSE-KMS: Keys Managed by AWS KMS
│   │   ├─ Uses AWS Key Management Service (KMS)
│   │   ├─ Supports key control and audit via CloudTrail
│   │   ├─ Header: `x-amz-server-side-encryption: "aws:kms"`
│   │   ├─ Limitations
│   │   │   ├─ Upload calls GenerateDataKey (KMS API)
│   │   │   ├─ Download calls Decrypt (KMS API)
│   │   │   └─ API request quotas: 5500, 10,000, or 30,000 requests/sec (region-dependent)
│   │   └─ Quotas can be increased through Service Quota Console
│   └─ SSE-C: Customer-Provided Keys
│       ├─ Fully managed keys by the customer
│       ├─ Amazon S3 does not store the keys
│       ├─ Requires HTTPS for secure communication
│       └─ Encryption key must be sent with each S3 request in HTTP headers
├─ Client-Side Encryption
│   ├─ Encryption and decryption handled by the client
│   ├─ Process
│   │   ├─ Client encrypts before upload to S3
│   │   └─ Client decrypts after download from S3
│   ├─ Managed key lifecycle by client
│   └─ Tool: Amazon S3 Client-Side Encryption Library
└─ Encryption in Transit (SSL/TLS)
    ├─ Ensures data security during transmission
    ├─ S3 Endpoints
    │   ├─ HTTP: No encryption during transit
    │   └─ HTTPS: Encrypts data during transit (recommended)
    ├─ HTTPS mandatory for SSE-C
    ├─ Most clients default to HTTPS
    └─ Force Encryption: Use policy `aws:SecureTransport` to enforce secure communication


Cross-Origin Resource Sharing (CORS)
├─ Overview
│   ├─ **Origin** = scheme (protocol) + host (domain) + port
│   │   ├─ Example: 
│   │   │   ├─ `https://www.example.com` (implied port 443 for HTTPS)
│   │   │   └─ `http://www.example.com` (implied port 80 for HTTP)
│   ├─ **CORS** is a web browser-based mechanism.
│   │   ├─ Allows web applications to request resources from other origins while visiting the main origin.
│   │   ├─ Example:
│   │   │   ├─ **Same Origin**: `https://www.example.com/app1` & `https://www.example.com/app2`
│   │   │   └─ **Different Origins**: `https://www.example.com` & `https://www.other.example.com`
│   └─ Protection Mechanism:
│       ├─ Cross-origin requests will only work if:
│       │   └─ The **other origin** allows requests through **CORS headers**.
│       └─ Example CORS Header: `Access-Control-Allow-Origin`
├─ CORS with S3 Buckets
│   ├─ When a client makes a cross-origin request on an S3 bucket:
│   │   └─ Correct **CORS headers** must be enabled on the bucket.
│   ├─ Configuration:
│   │   ├─ Allow a **specific origin** (e.g., `https://www.example.com`).
│   │   └─ Allow **all origins** using `*`.
│   └─ Common Exam Tip:
│       ├─ CORS-related considerations are frequently asked in exams.
│       └─ Understanding how to configure CORS in S3 is essential.
